# Design：M1 数据可行性验证（design.md）

> 技术设计。验证"官方数据能否支撑设计"。术语/口径依据 CONTEXT.md（D15/D16/D17），里程碑定位见 docs/roadmap.md。本任务**只读验证，不写功能代码、不建仓、不改 data/、不部署**。

## 边界（boundaries）

- **只读**：全部用现有只读工具——WebFetch / web-reader 读官网页面，curl 下 CSV，multimodal-looker 子代理识图。不装依赖、不建仓、不写主代码。
- **小样本**：每源取最近 2-3 期 + 抽查少量历史，不批量回补。
- **礼貌限速**：请求间隔，不高频并发触发 WAF。
- **产出是结论不是数据管线**：本任务不生成 data/ 下权威 CSV，只产出验证报告。

## 契约（本任务对下游的输出）

`research/feasibility-report.md`，含：
1. **口径对照表**：7 个数据源 × {地理粒度 / 时间粒度 / 指标是数值还是排序 / 年龄维度 / 载体格式(HTML/PDF/图片/CSV) / 历史深度}
2. **可行性结论**：每个验证目标标 可行 / 需降级 / 不可行
3. **对 data-fetch 的影响清单**：哪些字段确认可取、哪些要降级、哪些删除

下游 data-fetch 的 prd 回补范围据此定稿。

## 数据流（本任务内）

```
各源只读抓取/下载/识图 → 人工+工具核对字段与口径 → 填口径对照表 → 下三态结论 → 写 feasibility-report.md
```

## 权衡与回滚

- **为什么只读抽样而非直接全量回补**：回补是 data-fetch 的事；此处若发现口径不成立，回补代码会白写。抽样成本低、止损早。
- **回滚**：本任务无写操作，无需回滚；结论若为"多源不可行"，回到设计层修订 data-fetch/compute-index 的 prd，而非继续写代码。

## 兼容性

不改任何现有文件（CONTEXT/design/任务 prd 均不动）；只在本任务目录下新增 research/feasibility-report.md。对 data-fetch 的影响以"建议清单"形式提出，由用户决定是否改其 prd。
